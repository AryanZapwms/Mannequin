# Deployment

CI/CD runs on GitHub Actions. Images are built to GitHub Container Registry
(GHCR) and deployed to a VPS over SSH via Docker Compose.

## Pipeline

| Workflow | Trigger | What it does |
| --- | --- | --- |
| `ci.yml` | every push + every PR | `npm ci` → lint → typecheck → test → build |
| `deploy.yml` | push to `main`, or manual | runs CI, builds the image, pushes to GHCR, restarts the container on the VPS |

`deploy.yml` calls `ci.yml` as a gate, so a failing test or type error never
reaches production.

## Zero-downtime deploys (blue/green)

Two containers are defined, `blue` on `127.0.0.1:3001` and `green` on
`127.0.0.1:3002`. Exactly one serves traffic; Nginx decides which by way of a
generated upstream file. `scripts/deploy.sh` does the swap:

1. Reads `.active-color` to find the live colour, targets the other one.
2. Starts the idle colour on the new image — **the live one keeps serving.**
3. Polls the container `HEALTHCHECK` for up to 150s.
4. **Only if healthy**, rewrites `nginx/upstream.conf` and runs
   `systemctl reload nginx`. A reload is graceful: existing workers finish their
   in-flight requests while new ones pick up the new config, so no connection is
   dropped and there is no window where nothing is listening.
5. Waits 10s for the old colour to drain, then stops it.

If the new container never goes healthy, **Nginx is never touched** — the deploy
fails with the previous version still serving. That is the rollback: there is
nothing to undo, because traffic never moved.

Both `deploy.yml` and `rollback.yml` call this one script, so the two paths
cannot drift apart.

## Required GitHub secrets

Set under **Settings → Secrets and variables → Actions**.

| Secret | Example | Notes |
| --- | --- | --- |
| `SSH_HOST` | `203.0.113.10` | VPS IP or hostname |
| `SSH_USER` | `deploy` | Non-root user in the `docker` group |
| `SSH_KEY` | `-----BEGIN OPENSSH PRIVATE KEY-----…` | Private half of a key added to the server's `authorized_keys` |
| `SSH_PORT` | `22` | Optional, defaults to 22 |
| `DEPLOY_PATH` | `/srv/mannequincare` | Directory holding `docker-compose.yml` and `.env` |
| `NEXT_PUBLIC_RAZORPAY_KEY_ID` | `rzp_live_…` | Inlined at build time, so it must be a build secret |
| `NEXT_PUBLIC_APP_URL` | `https://mannequincare.in` | Same — baked into the bundle |

`GITHUB_TOKEN` is provided automatically; no setup needed.

> Only `NEXT_PUBLIC_*` values belong in GitHub. Every server-side secret
> (`MONGODB_URI`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `AUTH_SECRET`,
> Cloudinary, Gmail) lives in `.env` **on the server** and is never sent to CI.

## One-time server setup

```bash
# 1. Install Docker + compose plugin
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER"   # log out and back in

# 2. Create the deploy directory
sudo mkdir -p /srv/mannequincare && sudo chown "$USER" /srv/mannequincare
cd /srv/mannequincare

# 3. Copy docker-compose.yml from the repo, then create .env from .env.example
#    with real production values (chmod 600 .env)

# 4. Authenticate to GHCR once (or rely on the login step in the workflow)
echo "$GHCR_PAT" | docker login ghcr.io -u <github-username> --password-stdin

# 5. Let the deploy user reload Nginx without a password
sudo tee /etc/sudoers.d/deploy-nginx >/dev/null <<'EOF'
deploy ALL=(root) NOPASSWD: /usr/sbin/nginx -t, /bin/systemctl reload nginx
EOF
sudo chmod 440 /etc/sudoers.d/deploy-nginx
```

### Nginx

The upstream file is generated by the deploy script and lives in the deploy
directory (so the deploy user can write it without root). Seed it once:

```bash
mkdir -p /srv/mannequincare/nginx
printf 'upstream mannequincare_app {\n    server 127.0.0.1:3001;\n}\n' \
  > /srv/mannequincare/nginx/upstream.conf
```

Then in `/etc/nginx/sites-available/mannequincare`:

```nginx
include /srv/mannequincare/nginx/upstream.conf;

server {
    listen 443 ssl http2;
    server_name mannequincare.in www.mannequincare.in;

    # certbot --nginx fills these in
    ssl_certificate     /etc/letsencrypt/live/mannequincare.in/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mannequincare.in/privkey.pem;

    client_max_body_size 20M;   # product image uploads

    location / {
        proxy_pass http://mannequincare_app;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        "upgrade";
    }
}

server {
    listen 80;
    server_name mannequincare.in www.mannequincare.in;
    return 301 https://$host$request_uri;
}
```

The containers bind to `127.0.0.1` only, so they are unreachable except through
Nginx. The first `Deploy` run starts `blue` and points the upstream at it.

## Rollback

Every build is tagged with its commit SHA, so any past deploy can be restored
without rebuilding. There are three routes, in order of preference.

### 1. Automatic (no action needed)

A broken release never reaches traffic. The new colour has to pass its
healthcheck *before* Nginx is pointed at it, so a failed deploy leaves the
previous version serving and there is nothing to undo.

This covers crash-on-boot, a bad env var, an unreachable database — anything the
healthcheck catches. It does **not** catch a release that starts fine but is
broken in ways only users notice; for that, use route 2.

### 2. Manual, from GitHub

**Actions → Rollback → Run workflow**, then paste the commit SHA you want (or
`latest`). This redeploys an image that already exists in GHCR — no build runs,
so it works even when `main` is broken. It verifies the tag exists *before*
touching the running container, and health-checks the result.

Find the SHA from the commit list, or on the server:

```bash
cat /srv/mannequincare/.deployed-tag   # what is live right now
```

### 3. Manual, on the server

```bash
cd /srv/mannequincare
IMAGE_REPO=ghcr.io/varun240909/mannequincare.in ./scripts/deploy.sh <commit-sha>
```

Same blue/green path, so this is zero-downtime too. Never start containers by
hand with `docker compose up` — the script owns which colour is live, and
bypassing it desynchronises `.active-color` from the Nginx upstream.

**Instant revert, no image pull:** if the previous colour's container is still
around, just point Nginx back and reload — this is a sub-second flip.

```bash
printf 'upstream mannequincare_app {\n    server 127.0.0.1:3001;\n}\n' \
  > nginx/upstream.conf   # 3001 = blue, 3002 = green
sudo nginx -t && sudo systemctl reload nginx
echo blue > .active-color
```

> Rolling back the running image does **not** roll back the database. If the bad
> release changed a schema or migrated data, undo that separately.

## Post-deploy checklist

- Razorpay webhook points at `https://mannequincare.in/api/razorpay/webhook`
  and `RAZORPAY_WEBHOOK_SECRET` matches the dashboard.
- MongoDB Atlas network access allows the VPS IP.
- `AUTH_URL` / `NEXTAUTH_URL` matches the production domain.
